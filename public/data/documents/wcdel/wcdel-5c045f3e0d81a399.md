# Chapter01 Enemy And Dungeon Runtime Sync

## Goal

Move Chapter01 content from editor-only generated assets into real runtime usage, so enemy and dungeon definitions no longer stop at the config folder and begin driving the playable test slice directly.

## Scope

- Extended `SimpleEnemyController2D` with an `EnemyDefinition` binding path.
- Extended `SimpleRangedEnemyController2D` with an `EnemyDefinition` binding path.
- Bound enemy definitions into runtime application for:
  - HP
  - combat stats
  - move speed
  - detect range
  - attack range / preferred range
  - attack cooldown
  - damage baseline
- Extended `DungeonEntrance2D` with a `DungeonDefinition` reference and definition-driven confirm body.
- Extended `BossEntranceInteractable2D` with a `DungeonDefinition` reference and definition-driven boss entry summary.
- Updated `FoundationAssetUtility` so the Chapter01 test slice now wires:
  - `Meadow Slime` into the melee enemy prototype
  - `Poison Bee` into the ranged enemy prototype
  - `Grassleaf Cave` into the cave entrance
  - `Bee Nest` into the boss entrance

## Current Behavior

- The starter test slice still uses the same runtime enemy controllers, but those controllers now read Chapter01 definition assets instead of relying only on hardcoded editor-side numbers.
- Chapter01 cave and boss entrance prompts now surface dungeon-derived information such as recommended level, encounter count and dungeon description.
- The generated enemy and dungeon assets created in the previous slice now materially affect the playable prototype instead of only existing as future-facing placeholders.

## Boundaries

- This is still a lightweight runtime sync, not a full enemy factory or spawn-table system.
- Enemy definitions do not yet drive loot tables, AI archetype branching, attack patterns, boss phases or projectile elements beyond the current MVP controller behavior.
- Dungeon definitions do not yet load separate Unity scenes or formal encounter layouts; they currently feed runtime interaction copy and metadata only.
- The test slice still maps one melee prototype and one ranged prototype onto Chapter01 enemies rather than spawning the full chapter roster.

## Next Suggestions

1. Add a reusable enemy setup helper so multiple scene enemies can be spawned from different Chapter01 `EnemyDefinition` assets without duplicating editor code.
2. Introduce a small dungeon encounter marker component that references `DungeonDefinition` and can place named enemy packs from chapter content.
3. Expand `EnemyDefinition` only when runtime truly needs it next, such as drop rewards, projectile element overrides or elite/boss-specific feedback tuning.
4. Once multiple real scenes exist, let `DungeonDefinition.ScenePath` participate in actual load/transition flow instead of remaining metadata.
