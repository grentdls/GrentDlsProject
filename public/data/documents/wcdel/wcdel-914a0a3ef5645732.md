# DNF Side Scroll Controls MVP Sync

## Goal

Move the current player control stack from a top-down ARPG prototype toward a DNF-style side-scrolling beat'em up control MVP while preserving the existing project architecture.

This round focuses on landing a playable action skeleton rather than a full combat rewrite.

## Scope

### Input Semantics

Extended player input semantics toward DNF-style action control:

- move
- attack
- jump
- dodge
- interact
- skill 1~4
- ultimate
- pause

`GameInputReader` now exposes jump and ultimate input entry points in addition to the previous action set.

### State Flow

Expanded `PlayerActionState` with DNF-relevant action states:

- `Jump`
- `Fall`
- `Land`
- `AirAttack`
- `Ultimate`
- `Launch`
- `Down`
- `GetUp`

`PlayerStateController` now evaluates:

- airborne state
- launch / knockdown / get-up state
- air attack state
- ultimate cast state

### Jump / Airborne Runtime

Added `PlayerJumpController` to provide a dedicated airborne runtime layer for:

- jump start
- rise
- fall
- landing recovery
- launch arc
- downed duration
- get-up recovery

The component currently uses a visual vertical offset on the `Visual` child so the runtime can present jump / launch / knockdown phases without requiring a new rendering stack first.

### Combat Control

Updated `PlayerCombatController` so the MVP now supports:

- three-hit combo continuation timing
- combo reset timing
- air attack timing
- reuse of current combo config from character config assets
- attack-chain input buffering
- config-driven cancel windows for next attack / skill / dodge / jump
- fallback cancel timing when action-level cancel windows are still missing

### Skill / Ultimate Entry

Updated `PlayerSkillController` with:

- ultimate skill slot support
- separate ultimate cast duration
- state transition into `Ultimate`
- dodge-cancel support for non-ultimate skill recovery
- ultimate super armor and key-frame invincibility window

At the MVP layer, the ultimate currently reuses the existing area-skill emission path instead of introducing a separate cinematic finisher system.

### Hit / Launch / Down Logic

Updated `PlayerHitReactionController` so received damage can now branch into:

- hit stun
- knockback
- launch
- down
- get-up

The hit-reaction layer now also respects:

- dodge invincibility
- ultimate protection windows
- action-level super armor / anti-interrupt flags
- get-up invincibility

If the current action is protected, hit state entry and knockback are skipped so the runtime better matches the DNF control design.

### Input Buffer Runtime

Added `PlayerInputBuffer` as a lightweight runtime bridge between raw input and action execution.

Current buffered actions:

- attack
- jump
- dodge
- skill 1~4
- ultimate

Current default durations aligned with the DNF control design doc:

- attack: `0.25s`
- jump: `0.15s`
- dodge: `0.12s`
- skill: `0.25s`
- ultimate: `0.3s`

These timings are now sourced through `CharacterConfigDefinition` runtime config blocks and pushed by `CharacterConfigRuntimeBridge`, so the current hand-feel tuning is no longer locked to controller-side serialized defaults.

`PlayerActorController` now:

- tries to execute immediately
- buffers failed action requests when the current state cannot accept them
- consumes buffered actions when the state becomes valid again
- clears buffers on death / hit / launch / knockdown transitions

Launch currently uses a knockback-distance threshold to enter the airborne launch branch.

## Scene / Config Integration

Updated default starter-scene player setup to include:

- `PlayerJumpController`
- `PlayerInputBuffer`
- runtime bridge wiring from `CharacterConfigRuntimeBridge` into jump config

This keeps the existing sample hero config as the main tuning entry for:

- move speed
- dash
- combo actions
- skill entries
- jump tuning
- attack buffer timing
- combo reset timing
- fallback cancel windows
- skill / ultimate input buffer timing
- skill dodge-cancel timing
- ultimate protection timing
- launch threshold and get-up invincibility

## Side-Scroll Movement Runtime

Updated `TopDownCharacterMotor2D` so the current player runtime now behaves as a DNF-style side-scroll control MVP instead of a free top-down movement plane.

Current movement rules:

- horizontal input is the main movement axis
- vertical input is treated as up / down lane movement and can be disabled by `CharacterMovementConfig.CanMoveUpDown`
- facing is resolved from the horizontal axis and defaults to right
- ground and air movement both use the configured movement multipliers
- action direction for normal attack / skill-facing logic resolves to left or right
- dodge direction can still use diagonal or vertical lane input when available

`CharacterConfigRuntimeBridge` now pushes `CanMoveUpDown` into the motor together with move speed and acceleration settings, keeping the lane movement switch in character config assets instead of hardcoding it in controller logic.

Updated action direction users:

- `PlayerActorController`
- `PlayerCombatController`
- `DodgeController2D`
- `MeleeAttackEmitter`

This keeps normal attack hit tests and buffered action direction aligned with the side-scroll facing model.

## Current Boundaries

- movement now follows side-scroll main-axis rules, but it is not yet a full dedicated 2.5D lane collision system
- jump uses visual lift plus state logic, not a separate Z-axis collision model yet
- attack hit logic is still prototype overlap-based logic
- air skill branching exists at the state/input level, but full differentiated air-skill runtime behavior is not complete yet
- ultimate currently shares the basic skill emission path
- animation events, SFX / VFX frame events and frame-perfect hitbox authoring are not wired yet
- super armor / invincibility are available in runtime but still need deeper per-action authoring coverage
