# 编码规则

## 通用规则

- 优先复用现有 URP 2D、Input System、Unity 原生组件
- 不引入新依赖，除非任务明确要求
- 不写“第二套平行系统”
- 代码优先清晰、稳定、可查，不追求过早抽象

## C# 规则

### 命名

- 类名、方法名、属性名使用 `PascalCase`
- 私有序列化字段使用 `_camelCase`
- 常量使用 `PascalCase` 或 `UPPER_SNAKE_CASE`，同一文件内保持一致
- 布尔字段用 `is`、`has`、`can` 等语义前缀

### 命名空间

统一使用：

```csharp
WCDEL.Game
```

按模块细分子命名空间。

### 组件职责

- 一个组件解决一个主要问题
- 输入读取、移动、战斗、交互、动画驱动尽量拆开
- 不要把玩家所有逻辑堆进一个超大 `PlayerController`

### 序列化与 Inspector

- 可调参数优先 `SerializeField`
- 静态配置优先 `ScriptableObject`
- 仅在确有必要时使用 `public` 字段

### 依赖获取

优先级：

1. Inspector 注入
2. `GetComponent`
3. 明确的查找入口

避免在 `Update` 中反复做全局查找。

### 数据与逻辑

- 定义类不处理场景行为
- 运行时行为不硬编码大批数值
- 尽量把战斗数值、移动参数、区域等级做成可配置项

### 日志

- 调试日志必须可删除或可关闭
- 不要把高频 `Debug.Log` 留在正式循环里

## Unity 规则

### 生命周期

- `Awake`：缓存依赖、基础初始化
- `OnEnable`：事件订阅、输入启用
- `Start`：依赖其他对象存在后的初始化
- `Update`：输入和非物理逻辑
- `FixedUpdate`：刚体与物理逻辑
- `OnDisable`：取消订阅、输入停用

### 物理

- 2D 角色移动优先 `Rigidbody2D`
- 不混用 3D 物理组件
- 移动、冲刺、击退逻辑统一围绕 `Rigidbody2D`

### 输入

- 使用 `Input System`
- 行为层读取动作，不直接在业务逻辑里写按键码
- PC、手柄、移动端输入设计尽量复用同一语义动作

### UI

- 战斗 HUD 与后台菜单分开
- 世界空间 UI 和屏幕空间 UI 分开
- 移动端点击区域必须足够大

## 文件组织

- 运行时代码只放在 `Assets/Game/Runtime`
- 编辑器代码只放在 `Assets/Game/Editor`
- ScriptableObject 定义与使用逻辑分目录存放

## 禁止项

- 不要在未经确认的情况下删除旧逻辑
- 不要随意改动资源路径
- 不要手工大改场景 YAML 结构
- 不要在一个文件里堆多种无关类型

## 注释规则

- 仅在逻辑不直观时写短注释
- 注释解释“为什么”，不是“代码字面在做什么”

## 验证规则

每次改动至少完成以下之一：

- 编译验证
- 场景级自测
- 数据结构校验
- 文档与实现对照检查
