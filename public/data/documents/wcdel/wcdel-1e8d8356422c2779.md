# World Interaction Overlay Sync

## Goal

Add a reusable world interaction overlay MVP so scene interactions no longer rely only on runtime logs, and can surface dialogue, confirm and result UI in a unified way.

## Scope

- Added `WorldInteractionOverlayPresenter` as a lightweight screen-space interaction overlay layer.
- Supports three MVP overlay modes:
  - `Dialogue`
  - `Result`
  - `Confirm`
- Locks `GameSession.FlowState` to `Dialogue` for blocking interactions and restores previous flow state on close.
- Pauses `Time.timeScale` for blocking overlay interactions and restores it on close.
- Integrated current prototype world interactions:
  - `NpcDialogueInteractable2D`
  - `QuestBoardInteractable2D`
  - `ShopInteractable2D`
  - `TeleportPoint2D`
  - `DungeonEntrance2D`
  - `RewardChestInteractable2D`
- Extended `Setup Starter Test Slice` to auto-create `Canvas_Interaction`, `SafeAreaRoot` and `WorldInteractionOverlay`.

## Current Behavior

- NPC interaction now opens a dialogue-style overlay instead of only logging text.
- Quest board now shows accept / complete result feedback.
- Shop interaction now shows:
  - not-enough-gold result prompt
  - purchase confirm prompt
  - purchase success result
- Dungeon entrance now shows a confirm prompt before entering.
- Teleport and chest interactions now show result feedback overlays.

## Boundaries

- This is still a shared MVP interaction layer, not a final full-page shop, dialogue tree or reward inventory UI.
- Item purchase still uses the existing sample equipment prototype path and runtime data mutation.
- Dialogue currently uses static text blocks, not line-by-line playback or branching options yet.
- Result overlays do not pause time by default; confirm and dialogue overlays do.

## Next Suggestions

1. Extend the overlay with error-state styling and icon variants for warning, reward and locked-condition prompts.
2. Split shop, quest accept and boss entrance into dedicated presenters once their data and button flows become more complex.
3. Add direct bridge support for shrine restore, ability unlock and area-discovery notifications.

## 2026-05-15 - Quest And Shop Detail Card Upgrade

### Scope
- Upgraded quest board interaction from direct accept result prompt to a lightweight quest detail choice card.
- The quest accept card now shows category, recommended level, target region, objective summary and reward summary before acceptance.
- Upgraded shop purchase confirmation from plain one-line confirm text to a lightweight item detail card.
- The shop confirm card now shows slot, rarity, required level, current gold, price and core equipment stat bonuses.
- Extended the overlay API with `ShowChoice(...)` as a semantic alias for reusable two-button detail card flows.

### Notes
- This remains inside the shared interaction overlay layer instead of creating dedicated full-screen quest or shop presenters.
- Quest completion is still using the simpler result prompt because it already acts like a reward handoff summary.
- The next natural step is reusing the same detail-card shape for boss entrance and shrine restore confirmation.

## 2026-05-15 - Shrine And Boss Risk Confirmation

### Scope
- Upgraded shrine interaction from immediate execution to a confirmable detail card flow.
- Shrine detail card now shows current HP/MP to full restore preview, respawn-point update note and optional gold cost.
- Added `BossEntranceInteractable2D` as a dedicated high-risk entrance prototype for boss-gate style interactions.
- Boss entrance detail card now shows boss name, target area, recommended level and warning summary before entry.
- Extended the starter test slice to auto-create a `BossGate` prototype using the new boss entrance interaction path.

### Notes
- This iteration keeps dungeon entrance and boss entrance as separate prototype paths on purpose, because their UX rules are diverging.
- Shrine blessing currently restores health and mana, and can optionally refresh respawn plus consume gold.
- The next natural step is adding condition-lock prompts for underleveled boss entry and blocked shrine/teleport usage.

## 2026-05-15 - Teleport Activation And Travel Confirmation

### Scope
- Upgraded `TeleportPoint2D` from immediate teleport to an activation-first interaction flow.
- First interaction on an inactive teleport point now unlocks that point and shows a result overlay instead of moving the player immediately.
- Re-interacting with an activated teleport point now opens a lightweight teleport detail card before travel.
- Added destination activation checks so linked portal travel can be blocked with an explicit reason when the target point is still undiscovered.
- Added a combat-state restriction message path so teleport cannot execute while the session is in `Combat`.
- Extended map runtime state with activated teleport-point tracking that persists independently from respawn-point activation.
- Updated the starter test slice so the two field portals demonstrate activation-first travel, while cave exit remains an immediate return-type portal.

### Notes
- This is still an MVP detail-card flow inside the shared interaction overlay, not the final full teleport list UI from the design document.
- Current blocking reasons cover combat and inactive target point; dungeon-wide, boss-wide and story-lock restrictions can layer onto the same path later.
- Teleport-point activation is now stored separately from respawn activation so shrine, checkpoint and fast-travel rules can evolve independently.
