# DNF Side Scroll Controls Completion Sync

## Goal

Continue the previous DNF-style side-scroll control migration and close the main gaps between the runtime behavior and `Docs/dnf_style_character_basic_controls_design.md`.

This round focuses on making the existing control stack actually consume the DNF authoring data that was already present in character config assets.

## Completed In This Round

### Hit Request Data Flow

Extended `DamageRequest` so runtime hit processing now carries:

- `HitHeight`
- `HitType`
- `LaunchPower`

This lets authored action data drive launch / knockdown / low-hit dodge rules instead of reducing every attack to the same generic hit reaction.

### Jump / Airborne Rules

`PlayerJumpController` now supports:

- config-driven `CanJump`
- low-height ground-attack dodge checks
- quick-recover / get-up input window
- get-up invincibility timing bridge from hit-reaction config
- explicit launch phase exposure

The airborne layer can now reject low attacks while the player is high enough in the jump arc, matching the DNF control doc much more closely.

### Hit / Launch / Down / Get-Up Flow

`PlayerHitReactionController` now interprets authored hit metadata:

- `Launch` hit type enters launch / down flow
- `Knockdown` hit type can force downed flow
- launch height and launch duration can come from authored data
- hit-reaction config now pushes quick-recover capability into jump runtime

### Dodge Runtime Completion

`DodgeController2D` now consumes more of the authored dash config:

- `CanDash`
- post-dash recovery time
- readiness blocked during recovery

This makes dash availability and post-dash control recovery match the config asset instead of only using distance / cooldown.

### State Machine Corrections

`PlayerStateController` now correctly resolves:

- `Launch`
- `Down`
- `GetUp`
- `CanJump` gating from jump config
- `CanDodge` gating from dash config

It also avoids collapsing launch into generic knockback before the jump controller gets a chance to expose the airborne launch state.

### Attack Authoring Consumption

`PlayerCombatController` and `MeleeAttackEmitter` now consume the current action's first authored `DamageEvent` for:

- hitbox offset / size approximation
- damage type
- element type
- hit stun
- knockback distance / duration
- hit height
- hit type
- launch power

This is still an overlap-based prototype attack system, but it now respects the DNF action authoring data far better than before.

### Hero Sample Config Coverage

`CharacterConfigSampleFactory` now applies a post-pass override for the hero sample config so the generated player setup includes:

- 3-hit grounded combo
- skill slot 1
- skill slot 2
- skill slot 3
- skill slot 4
- ultimate
- launch metadata on combo finisher
- low-hit metadata on poison skill
- knockdown metadata on ultimate

This avoids the earlier partial hero config generation issue where the sample config only fully wired the first skill and ultimate path.

## Remaining Boundaries

- the melee hit test still approximates authored hit boxes with a circle rather than true rectangle / capsule frame-accurate hitboxes
- interaction priority is still distance-first and does not yet fully match the detailed DNF document priority table
- sample hero config post-pass fixes the generated data flow, but the older helper functions in `CharacterConfigSampleFactory` still contain noisy legacy text and should be cleaned up in a dedicated pass
- air-skill specialization is still limited; the runtime now respects `CanAirSkill`, but separate authored airborne skill execution behavior is still shallow
- animation frame events, SFX frame events, VFX frame events, and hit-stop are still not fully wired into runtime execution

## Suggested Next Steps

1. Replace the current circle-based melee approximation with true authored `HitBox` shape evaluation.
2. Clean the legacy noisy helper bodies inside `CharacterConfigSampleFactory` now that hero generation is stabilized by the override pass.
3. Add interaction priority groups so quest NPC / chest / dungeon entrance ordering matches the control design document.
4. Expand airborne skill variants and recovery rules for more DNF-like combo routing.
